## 证据分类矩阵

| HAR 现象 | 优先结论 | 下一步 |
|---|---|---|
| 目标接口存在，脚本 0 次命中 | pattern、MITM 或脚本开关问题 | 对照完整 URL、query、版本和 comment |
| 命中脚本但响应未修改 | body 形状、编码或脚本异常 | 回放原始响应，确认 `$done` 路径 |
| API 缺失，仍加载新素材 | HTTPDNS、Type 3 TLS 或 QUIC/HTTP3 旁路 | 查 VIF、SNI、Alt-Svc、UDP 和 reply host |
| API 报网络错误，随后曝光旧素材 | 持久缓存失败回退 | 返回协议正确的成功空响应 |
| UI 先出现，之后才有请求 | App 本地落盘缓存 | 强退、清一次缓存、冷启动重测 |
| MP4 已 204，随后 M3U8/TS 成功 | 媒体格式回退链 | 按启动页面上下文补同族格式 |
| 原始响应完整，连续改写后页面报错 | 共享接口或字段误杀 | 删除宽改写，恢复透传并收窄广告接口 |

## 菜鸟缓存与混合广告接口

### 已验证规律

- 对广告主机做全协议拒绝会产生 `FAIL_SYS_NETWORK_ERROR`，客户端可能从持久缓存恢复旧广告。
- `show`、`show.login` 和 `batch.show` 是广告专用接口时，可在 request 阶段返回标准 MTop 成功空响应。
- `mshow` 同时承载广告和业务入口，只能过滤确认的展示结构。
- 广告位编号、素材 ID 和文案会轮换。`floatview*`、全图横幅、组合横幅、纯促销角标等结构比编号稳定。
- 过滤结构时必须锁定取件、寄件、身份码、服务入口和包裹字段保持不变。

### 判断缓存类型

1. 对比曝光时间和广告请求时间。
2. 检查多轮是否重复相同素材或 material。
3. 检查请求是否返回网络错误或成功空响应。
4. 新鲜 `currTimestamp` 的非空 mshow 数据属于当前下发；请求前出现且无新鲜响应更接近本地缓存。

## 京东开屏媒体轮换

### 已验证规律

- 启动视频可在不同数字业务路径间轮换，硬编码单一路径会定期失效。
- 主 MP4 被拦后，播放器可能回退到 HLS 的 M3U8 和 TS。
- 清理 App 缓存后仍应检查当前抓包。若 HAR 没有媒体请求，Surge 无法处理已落盘文件。
- 稳定分类应组合媒体 host/path 家族、京东媒体 UA 和主页面播放器 Referer 前缀。
- 商品详情视频、Discover 页面内容、直播流和共享 `jvod` 请求必须回归透传。

## 拼多多共享接口误杀

### 已验证规律

- 首页 hub 的宽字段删除会连同业务入口和补贴卡片一起消失。
- 首页刷新、个人中心和聊天可能复用 cells 类接口；单看 `refer_page_sn` 容易误判页面。
- 商品详情服务端响应可保持完整，但连续删除 `bottom_section`、`live_section` 等结构后客户端会显示服务器错误。
- 修复优先删除造成破坏的宽 Body Rewrite，让首页、搜索、刷新和商品详情完整透传。
- 聊天和个人中心去广告应使用专用接口，必要时通过 `tcp-connection = true` 接管原始 TLS。

## 可复用判断规则

1. 先验证模块确实加载，再分析规则是否覆盖目标请求。
2. 先用时间顺序区分新响应、失败缓存和本地缓存。
3. 先找稳定上下文或结构，再写规则。
4. 每次扩大匹配范围，都要增加至少一个业务保留测试。
5. 看到共享 endpoint 时，检查完整页面上下文；证据不足就透传。
6. 素材域通常是结果，配置或布局 API 更接近根因。
7. HAR 回放、配置解析和 Raw 哈希只能证明工程交付，设备 UI 仍需独立验收。
